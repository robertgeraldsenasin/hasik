# 04. Algorithms

Each section gives: purpose, how it works, pseudocode, parameters, complexity, pitfalls, and how to show it in the demo. Sections marked **HAND-WRITTEN** are written by Gerald (07_CONSTRAINTS.md); Claude Code may test and review them.

The one Sungka-specific trap that touches almost everything: **extra turns**. After a move, the same player may move again. Never assume sides alternate. Always read `state.toMove`.

---

## A1. Rules engine and move generation (HAND-WRITTEN)

**Purpose:** apply a move exactly per `RuleConfig`, fast enough for millions of calls.

**How:** a 16-slot `Uint8Array`, a precomputed `next[player][slot]` table (skips the opponent's store), and a single loop for sowing with relay pickups.

```
applyMove(state, house):
  s = copy(state.slots); p = state.toMove; steps = 0
  hand = s[house]; s[house] = 0; i = house
  loop:
    while hand > 0:
      i = next[p][i]; s[i] += 1; hand -= 1; steps += 1
      if steps > rules.maxSowSteps: throw / end turn
    if i == store(p) and rules.extraTurnOnStore: return (s, toMove = p)
    if isHouse(i) and s[i] > 1 and rules.relaySowing:
      hand = s[i]; s[i] = 0; continue loop        # relay
    if isOwnHouse(p, i) and s[i] == 1:
      o = 14 - i
      if s[o] > 0 or not rules.captureRequiresNonEmptyOpposite:
        gain = s[o] + (rules.captureIncludesLandingShell ? 1 : 0)
        s[store(p)] += gain; s[o] = 0; if captureIncludesLandingShell: s[i] = 0
    return (s, toMove = other(p))
```

Update the Zobrist hash incrementally on every slot change (A3).

**Complexity:** O(shells moved) per move. Relay sowing makes this unbounded in theory, so `maxSowSteps` exists.

**Pitfalls:** off-by-one on laps; forgetting to skip the opponent's store on every lap; a capture rule applied when the last shell landed on the opponent's side; end-of-game check happening before the extra-turn check.

**Demo:** a debug overlay that animates each drop and highlights relay pickups.

## A2. Perft (HAND-WRITTEN)

**Purpose:** a regression fingerprint for move generation. If the leaf count at depth d changes, the rules changed.

```
perft(state, depth):
  if depth == 0 or isTerminal(state): return 1
  total = 0
  for m in legalMoves(state): total += perft(applyMove(state, m).state, depth - 1)
  return total
```

Depth counts **moves** (plies), not turns, so an extra-turn move still costs one depth. Record golden values for depths 1-6 from the start position and a few fixed positions once the engine is verified, and lock them in a test.

## A3. Zobrist hashing (HAND-WRITTEN)

**Purpose:** a near-unique 64-bit key per position for the transposition table and repetition checks.

**How:** a table `Z[slot][count]` of random 64-bit values for 16 slots × counts 0..98, plus `Z_side` for side to move. Hash = XOR of `Z[slot][slots[slot]]` over all slots, XOR `Z_side` if player B to move.

**Incremental update:** when slot j goes from count c to c+1: `h ^= Z[j][c] ^ Z[j][c+1]`. Flip `Z_side` when the side to move changes (not on extra turns).

**Performance note:** JavaScript `BigInt` is slow. Store the key as two `Uint32` halves (`hi`, `lo`) generated by a seeded PRNG, XOR each half separately, and index the table with `lo & mask`.

**Pitfall:** generating keys with `Math.random` breaks reproducibility. Use the seeded PRNG (A12) with a fixed seed.

## A4. Minimax with alpha-beta, iterative deepening and a transposition table (HAND-WRITTEN)

**Purpose:** the main AI.

**Negamax with extra turns:** when the same player moves again, do **not** negate the child's score and keep the same alpha-beta window.

```
search(state, depth, alpha, beta):
  if timeUp(): abort
  if isTerminal(state): return terminalScore(state, perspective = state.toMove)
  if tablebase.covers(state): return tablebase.probe(state)            # A7, M2
  tt = TT.probe(state.hash)
  if tt and tt.depth >= depth:
    if tt.flag == EXACT: return tt.score
    if tt.flag == LOWER: alpha = max(alpha, tt.score)
    if tt.flag == UPPER: beta  = min(beta,  tt.score)
    if alpha >= beta: return tt.score
  if depth == 0: return evaluate(state)                                  # A5
  best = -INF; bestMove = none; alphaOrig = alpha
  for m in orderMoves(state, tt?.bestMove):                              # A6
    child = applyMove(state, m)
    sameSide = child.state.toMove == state.toMove
    d = sameSide and extraTurnExtension ? depth : depth - 1             # extension, capped
    score = sameSide ? search(child.state, d, alpha, beta)
                     : -search(child.state, d, -beta, -alpha)
    if score > best: best = score; bestMove = m
    alpha = max(alpha, score)
    if alpha >= beta: recordKiller(m, depth); updateHistory(m, depth); break
  flag = best <= alphaOrig ? UPPER : best >= beta ? LOWER : EXACT
  TT.store(state.hash, depth, best, flag, bestMove)
  return best
```

**Iterative deepening:** search depth 1, 2, 3... until the time budget runs out; keep the best move from the last completed depth. The TT makes earlier iterations nearly free and improves move ordering.

**Time management:** check the clock every 1,024 nodes. Soft limit = stop starting new depths; hard limit = abort mid-search and use the previous result.

**Transposition table:** fixed-size power-of-two array of entries `{keyHi, keyLo, depth, score, flag, bestMove}`. Replacement: two-tier (a depth-preferred slot and an always-replace slot). Size it in MB and expose it as a parameter.

**Extra-turn extension cap:** allow at most K consecutive non-decrementing extensions per line (K = 4 to start) to avoid explosion.

**Parameters:** `timeMs`, `maxDepth`, `ttSizeMB`, `extraTurnExtension` (bool), `K`.

**Complexity:** with branching factor ≤ 7 and good ordering, alpha-beta examines roughly the square root of the minimax tree.

**Demo:** the hint mode shows the principal variation, depth reached and nodes per second.

**Difficulty levels:**

| Level | Bot | Limit |
| --- | --- | --- |
| 1 | Random | none |
| 2 | Greedy (best immediate store gain) | none |
| 3 | Minimax | depth 3 |
| 4 | Minimax | 200 ms |
| 5 | Minimax + tablebase | 1,000 ms |

## A5. Evaluation function (HAND-WRITTEN)

**Purpose:** score non-terminal leaves from the side-to-move's perspective.

```
eval(state) =
    W_store   * (myStore - oppStore)
  + W_side    * (shellsOnMySide - shellsOnOppSide)
  + W_mobility* (myLegalMoves - oppLegalMoves)
  + W_extra   * (myImmediateExtraTurnMoves - oppImmediateExtraTurnMoves)
  + W_capture * (myBestImmediateCapture - oppBestImmediateCapture)
```

Start with `W_store = 100, W_side = 10, W_mobility = 5, W_extra = 30, W_capture = 20` and tune later (A11). Terminal scores use a large constant (e.g. ±100,000 ± final margin) so wins always beat heuristics.

**Pitfall:** whether `shellsOnMySide` is good depends on `remainingShellsGoTo`. Under "owner", shells on your side at the end are yours; under "capturer", it depends who ends the game.

## A6. Move ordering (HAND-WRITTEN)

Order: TT best move → moves whose last shell lands in own store (extra turn) → captures → killer moves at this depth → history heuristic score. Good ordering is what makes alpha-beta fast; measure nodes per depth with and without it and report the difference.

## A7. Retrograde-analysis endgame tablebase (HAND-WRITTEN, M2)

**Purpose:** perfect play when few shells remain on the board.

**Key insight:** stores never affect future moves. So the board-only state (14 house counts + side to move) fully determines the rest of the game. Define `V(state)` = best achievable *future* store gain for the side to move minus the opponent's future gain, including the end-of-game rule for remaining shells.

**State space:** with T shells across 14 houses, there are C(T+13, 13) layouts. For all T ≤ N:

| N | States per side (sum over T ≤ N) |
| --- | --- |
| 6 | 38,760 |
| 8 | 319,770 |
| 10 | 1,961,256 |

Start with N = 8. Store `V` as `Int8` in a flat array.

**Indexing:** map a layout to an array index with the combinatorial number system (rank compositions of T into 14 parts), plus an offset for each T and side. Unranking is needed only for generation; probing needs ranking.

**Generation by layers of T, ascending:**
- Moves that bank shells (into a store or by capture) lead to smaller T, already solved.
- Moves that keep T the same (e.g. relay ending on an empty opponent house) stay in the same layer, and cycles are possible.
- Solve each layer by value iteration: initialize all states as unknown; repeatedly compute `V` for states whose same-layer children are all known; iterate until nothing changes. Remaining states are in cycles: resolve with bounded value iteration (cap iterations), and mark any still unresolved as `UNKNOWN` so search falls back to normal evaluation.

**Probe:** in search, if board total ≤ N, return `V` (converted to the search's score scale) instead of searching deeper.

**Demo:** a stat line, "Tablebase: solved 639,540 positions (N = 8) in X s", plus a toggle that shows when the AI is playing perfectly.

**Pitfall:** the extra-turn rule means "side to move after the move" may not flip; handle sign exactly as in A4.

## A8. Monte Carlo Tree Search, UCT (HAND-WRITTEN)

**Purpose:** a second AI built on different principles, to compare against minimax.

```
mcts(rootState, budget):
  root = Node(rootState)
  while budget left:
    node = root
    # 1. selection
    while node.fullyExpanded and not node.terminal:
      node = argmax_child( child.W/child.N + C * sqrt(ln(node.N) / child.N) )
    # 2. expansion
    if not node.terminal: node = node.expandOneUntriedMove()
    # 3. simulation (seeded PRNG; epsilon-greedy playout policy optional)
    result = playout(node.state)          # final margin or win/draw/loss
    # 4. backpropagation
    while node: node.N += 1; node.W += valueFor(node.playerWhoMovedInto, result); node = node.parent
  return child of root with the most visits
```

Store at each node which player made the move into it, so backprop credits the right side even with extra turns. Parameters: `C` (start at 1.41), budget in playouts or ms, playout policy (random vs epsilon-greedy with ε = 0.1). Report win rate vs minimax at equal time.

## A9. Glicko-2 ratings (HAND-WRITTEN)

**Purpose:** rate bots and players with an uncertainty band (RD) and volatility, which is better than plain Elo for few or irregular games.

**Steps per rating period** (Glickman's algorithm): convert rating and RD to the Glicko-2 scale (μ, φ); compute v (estimated variance from game outcomes) and Δ (estimated improvement); solve for the new volatility σ' with the Illinois (regula falsi) method using system constant τ (start at 0.5); update φ* then φ' and μ'; convert back. Players with no games only have their RD grow.

**Defaults:** rating 1500, RD 350, σ 0.06, τ 0.5. Rating period = one tournament or one day of games.

**Tests:** reproduce the worked example from Glickman's Glicko-2 paper to the stated precision.

**Demo:** leaderboard with rating ± 2·RD.

## A10. SPRT, the CI strength gate (math HAND-WRITTEN)

**Purpose:** decide with controlled error rates whether engine B (the PR) is stronger than engine A (main), using as few games as possible. This is how Stockfish's testing framework accepts or rejects patches.

**Hypotheses (in Elo):** H0: elo ≤ elo0, H1: elo ≥ elo1. Error rates α (false accept) and β (false reject).

**Bounds:** `lower = ln(β / (1 − α))`, `upper = ln((1 − β) / α)`. With α = β = 0.05, both are about ±2.94.

**Log-likelihood ratio (normal approximation, trinomial W/D/L):**

```
score(elo) = 1 / (1 + 10^(-elo / 400))
s0 = score(elo0); s1 = score(elo1)
N = W + D + L
x̄  = (W + 0.5 D) / N
var = (W(1 − x̄)² + D(0.5 − x̄)² + L(0 − x̄)²) / N
LLR = N * (s1 − s0) * (2x̄ − s0 − s1) / (2 * var)
stop when LLR ≥ upper (accept H1) or LLR ≤ lower (accept H0)
```

**Game design:** play in **pairs** with the same opening and colors swapped (A12, A13) to cancel first-player advantage and reduce variance. Upgrade path: the pentanomial model over game pairs, which is more accurate for paired games.

**Two gate modes:**

| Mode | When | Bounds | PR fails if |
| --- | --- | --- | --- |
| Gainer | PR claims a strength improvement (label `engine:gainer`) | [0, 5] Elo | H0 accepted |
| Non-regression | Any other change touching engine/bots | [−10, 0] Elo | H0 accepted (meaning it got weaker) |

**CI budget:** cap at a maximum number of game pairs or a time limit. If inconclusive at the cap, report "inconclusive" and require a maintainer override label, so CI can't silently pass a weaker engine.

**Also report:** estimated Elo difference with a 95% confidence interval, W/D/L, and games played.

## A11. SPSA evaluation tuning (stretch)

**Purpose:** tune the eval weights (A5) automatically, the way engine developers do.

```
θ = initial weights
for k = 1..K:
  Δ = random ±1 vector
  θ+ = θ + c_k Δ ; θ- = θ − c_k Δ
  r  = matchScore(engine(θ+) vs engine(θ-), games = G)   # in [0, 1]
  g  = (r − 0.5) / (c_k * Δ)                              # elementwise
  θ  = θ + a_k * g
```

Use decaying `a_k`, `c_k`. Validate the tuned weights with an SPRT run against the hand-picked weights.

## A12. Seeded PRNG and opening sampler (hand-written PRNG)

- PRNG: mulberry32 or xoshiro128**, with the seed stored in every game record.
- Opening sampler: from the start position, play 2-4 random legal moves with a seeded PRNG; keep openings where a depth-4 search evaluates within ±50 points (roughly balanced). Generate a fixed opening file (e.g. 500 openings) and commit it, so SPRT and arena runs are reproducible.
