# 05. Methodology

How the project is built, tested and measured, so every number in the README can be reproduced and defended.

## Development method

- **Spec first, then core, then shell.** Rules doc → engine with tests → bots → arena → UI and services.
- **Plan mode for every feature** in Claude Code; the approved plan goes into `docs/decisions/` as an ADR when it involves a real choice.
- **Small pull requests**, each with a description, a linked issue, and green CI. Partner reviews before merge (if the duo works on it), plus `@claude` review via GitHub Actions.
- **Hand-written core, assisted shell** (07_CONSTRAINTS.md).
- **Debug log:** every non-trivial bug gets a short entry in `docs/debug-log.md` (symptom, cause, fix, test added).

## Test pyramid

| Level | Tool | What it covers | Runs |
| --- | --- | --- | --- |
| Unit | Vitest | Every rule in the 02 checklist; Zobrist incremental vs full recompute; TT replacement; Glicko-2 worked example; SPRT LLR against hand-computed values | Every push |
| Property-based | fast-check | Over thousands of random games: shell conservation (always 98); legal moves are exactly non-empty own houses; game always terminates; incremental hash equals recomputed hash; `applyMove` never mutates its input | Every push |
| Golden / regression | Vitest snapshots | Perft counts at depths 1-6 from fixed positions; tablebase checksum for N = 6 | Every push |
| Search correctness | Vitest | Alpha-beta returns the same value as plain minimax at small depths on random positions; TT on/off gives the same best value; tablebase value equals full search on covered positions | Every push |
| Strength | SPRT tool | New engine vs main (A10) | PRs touching engine/bots |
| Integration (M2) | Vitest + testcontainers or Compose | Server rejects illegal moves; reconnect resumes state; game persisted with all moves | Every push to main, PRs touching server |
| End-to-end | Playwright | Load page, start game vs level 3, make 3 moves, see bot respond | Every PR (one smoke test) |

Failure-path tests to include: illegal house index, moving out of turn, stale `clientPly`, malformed WebSocket message, worker crash mid-search (UI shows retry), database down (server degrades to in-memory play).

## Benchmarking

`tools/bench` prints a table and writes JSON:

- Perft speed (moves per second) at depth 6 from the start position
- Search nodes per second, average depth reached at 200 ms and 1,000 ms
- Effect of each technique, measured as nodes needed to finish a fixed depth: plain minimax → + alpha-beta → + move ordering → + TT → + extensions
- Tablebase generation time and size for N = 6 and 8
- (Stretch) TS vs WASM nodes per second

Always state the hardware (CPU model, RAM, OS, Node version) in the README results table. Run each benchmark 5 times and report the median.

## Strength evaluation

**Round-robin arena (results table in README):** Random, Greedy, Minimax (200 ms), Minimax (1,000 ms), Minimax + tablebase (1,000 ms), MCTS (200 ms), MCTS (1,000 ms). 200 game pairs per pairing from the fixed opening file. Report score, W/D/L and Elo with 95% intervals, plus Glicko-2 ratings.

**Ablations:** each technique's Elo contribution, measured by SPRT or fixed-length matches (TT on/off, ordering on/off, tablebase on/off).

**Human check:** log human-vs-bot results from the live site (M2) by level; report the bot win rate per level once there are enough games. Never invent numbers.

## Reproducibility

- Every game stores its seed, opening ID, rules config, bot versions (git SHA) and limits.
- The opening file and the PRNG are committed; the same command regenerates any table.
- Results are JSON lines in `results/`; README tables are generated by a script, not typed by hand.
- Time-limited searches vary with hardware load, so strength results use fixed node counts or depths when comparing in CI, and time limits only for "real play" numbers.
